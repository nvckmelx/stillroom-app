# Архитектура

## Почему своя лёгкая CMS на PHP + MySQL

| Вариант | Почему нет / да |
|---|---|
| Strapi, Directus, Payload (Node.js headless CMS) | Нужен постоянно работающий Node-процесс и 1–2 ГБ памяти — на Hostinger это VPS или отдельные тарифы с Node.js; дороже и сложнее в обслуживании. |
| WordPress | Работает на любом Hostinger, но тянет тяжёлую тему/плагины, а сайт и Android-клиент пришлось бы переписывать под его REST; лишняя поверхность атаки. |
| **Своя CMS на PHP 8.2 + MySQL (выбрано)** | Hostinger изначально рассчитан на PHP + MySQL + cron: работает на любом тарифе без доплат. Нет зависимостей (composer/npm не нужны), один код для сайта, API и админки. Текущий стек проекта — ванильный JS + Capacitor — сохраняется без сборщиков. |

## Как всё связано

```
           ┌──────────── Hostinger ────────────┐
Админка ─► │ /admin (PHP, сессии, CSRF, роли)  │
           │        │                          │
           │        ▼                          │
           │ MySQL: tracks, collections, …     │──► storage/backups/*.zip (cron)
           │ public_html/uploads: аудио, фото  │
           │        │                          │
           │        ▼                          │
           │ GET /api/v1/catalog (JSON, ETag)  │
           └───────┬───────────────┬───────────┘
                   ▼               ▼
        Сайт (тот же домен)   Android-приложение (Capacitor, тот же JS-клиент)
        каталог встроен в     берёт каталог из API при запуске и каждые 5 мин,
        HTML + SEO            кэширует; без сети — встроенный офлайн-каталог
```

## Модель данных

- `tracks` — опубликованные значения в колонках, правки опубликованного трека в `draft` (JSON) до нажатия Publish.
  Статусы: `draft` (никогда не публиковался) → `published` → `unpublished` (скрыт).
- `categories`, `tags`, `track_tags` — категории (порядок, видимость) и теги.
- `collections`, `collection_tracks` — подборки с порядком; та же схема черновиков.
- `settings` — документы `site` и `home` (published + draft JSON).
- `media` — загруженные файлы (тип, путь, MIME, размер, длительность, размеры).
- `users`, `login_attempts`, `audit_log` — пользователи, защита от перебора, журнал действий.

Трек играет **загруженный файл** (`audio_media_id`) или **встроенный звук** (`engine` — один из 33 генеративных пресетов),
а фон — одна из **33 сцен** `backgrounds.js` (`scene`). Исходный каталог перенесён без потерь: 33 трека с теми же
названиями, подписями, описаниями, звуками и соответствием sound ID → background ID (5 ID отличаются названием:
relaxation→deep-relaxation, lofi→lo-fi-chill, spa→spa-yoga, morning→gentle-morning, forest-night→forest, NNNhz→hz-NNN).

## Публичный API (только чтение)

| Запрос | Ответ |
|---|---|
| `GET /api/v1/catalog` | Всё сразу: site, home, categories, tags, collections, tracks. ETag + `max-age=60`. |
| `GET /api/v1/tracks?q=&category=&tag=&collection=` | Поиск и фильтры. |
| `GET /api/v1/tracks/{slug}` | Один трек. |
| `GET /api/v1/scenes` | 33 сцены фона. |
| `GET /api/v1/health` | Состояние. |

`?preview=1` отдаёт черновики только при активной сессии администратора (тот же домен); иначе игнорируется.
CORS открыт только на чтение (`GET`), чтобы приложение могло читать каталог.

## Безопасность

- Пароли: Argon2id (`password_hash`), сессия httpOnly + SameSite=Lax (+Secure на HTTPS), новый ID сессии при входе, тайм-аут 8 ч.
- CSRF-токен на каждой форме админки; роли `admin`/`editor` проверяются на сервере на каждой странице.
- 5 неудачных входов за 15 минут с одного IP/email → блок; время ответа не выдаёт, существует ли email.
- Загрузки: белый список расширений, MIME через `finfo` **и** проверка сигнатуры файла, лимиты размера,
  случайные имена; картинки перекодируются GD в WebP (метаданные и «вложения» удаляются).
  В `uploads/.htaccess` запрещено исполнение скриптов и отдача HTML/SVG/JS.
- Секреты только в `.env` вне `public_html`; `.env`, база, бэкапы и загрузки в `.gitignore` (репозиторий публичный).
- Админка: CSP, `X-Frame-Options: DENY`, `noindex`; публичные страницы: `nosniff`, `Referrer-Policy`.
- Аудит-лог: вход, создание, публикация, снятие, удаление, бэкапы.

## Клиент (сайт + приложение)

`server/public/assets/js`: `app.js` (маршруты, страницы, плеер-бар, очередь, таймер, избранное),
`listen.js` (комната прослушивания — прежний дизайн: категории сверху со скользящим стеклянным выделением и свайпом,
свайп контента между треками, точки и счётчик, tap-to-play), `player.js` (очередь, repeat all/one/off, громкость,
таймер сна с затуханием, Media Session), `sound.js` (исходный генеративный движок без изменений), `world.js` +
`backgrounds.js` (33 сцены Codex; движение плавно останавливается ~2 с на паузе, reduced motion уважается),
`catalog.js` (загрузка каталога, ETag, кэш, превью), `thumbs.js` (миниатюры сцен).
Избранное и громкость хранятся на устройстве (localStorage) — это настройки пользователя, не данные CMS.
PWA: `manifest.webmanifest` (имя из CMS) и `sw.js` (оболочка офлайн; аудио не кэшируется).

## Что проверено (автотесты в браузере, SQLite)

- Вход → новый трек с аудио и обложкой (с телефона, 390 px) → черновик скрыт из API и сайта (404) → превью видит только
  админ → публикация → трек на сайте (категория, поиск, SEO, воспроизведение файла) и в приложении с другого origin
  (CORS) без пересборки → правка опубликованного не видна до публикации → снятие с публикации убирает его везде.
- Подборки, главная, настройки сайта (имя, ссылки, логотип, SEO) — черновик/превью/публикация; порядок категорий; sitemap, robots, manifest.
- Отказ поддельного MP3 и PHP-файла под видом PNG; редактор получает 403 на Users/Site/Backups; CSRF (419); блок перебора.
- Веб-установщик на пустой базе (неверный токен, установка, самоотключение); бэкап и восстановление.
- 360 / 390 / 768 / 1440 px: нет горизонтальной прокрутки ни на одной странице сайта и админки, зоны касания ≥ 42–44 px.
- Регрессии комнаты прослушивания: 33/33 сцены, статичный фон на паузе, остановка ~2 с, свайпы не включают/выключают звук,
  свайп категорий, скрытая вкладка, immersive-режим, таймер, очередь, repeat, reduced motion.
- **MySQL** в песочнице недоступен: миграции, импорт, создание админа и бэкап на реальном MySQL 8 проверяет CI (job `backend`).
